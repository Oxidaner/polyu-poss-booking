## 拿到真实「提交预订」抓包 + cURL 导入器（同日 22:40）
- 用户贴出真实提交请求，关键事实（都是猜不出来的）：
  - 端点是 **POST /starspossfbstud/secure/ui_make_book/make_book.do**（与页面 GET 同地址），Content-Type: application/x-www-form-urlencoded，是 document 导航型提交（Sec-Fetch-Mode: navigate），响应应是 HTML 结果页而非 JSON。
  - 日期时间格式 **`18 Sep 2026 14:30`**（编码后 `18+Sep+2026+14%3A30`），即 `%d %b %Y %H:%M` —— 必须把 locale 钉在 C，否则 zh_CN 下 %b 出「9月」。
  - 字段 `boMakeBookFacilities[0].facilityId=233`：**facilityId 必须来自 timetable.json**（所以当初要 showCourtAreaDetails=true）。facilityId 很可能挂在分组父节点上 → 解析器已改为继承祖先标量字段。
  - `searchFormString` 的值内部**嵌了一整串 URL 编码参数**（内含 fbUserId/ctrId）→ 不递归替换就会残留旧 ctrId，换馆抢位会抢错。
  - 成功判定关键词未校准（响应体没见过），`success_keywords` 待用一次真实响应校准。
- 新增 `calibrate.py`：粘贴 cURL → 自动模板化 → 输出 `booking.curl` + 逐字段审查表。识别 csrf/fbUserId/ctrId/facilityId/slotId、日期/时间/组合日期时间、嵌套查询串。
- **设计抉择（重要）**：请求体**不做「解码→重编码」**，只做纯文本替换并原样保留浏览器编码字节——因为 searchFormString 的值内部含裸 `&`/`=`，解码重解析会把字段切碎。需要编码的占位符写成 `{key:url}`。渲染后逐字节比对通过（URL+body 完全一致）。
- 踩过的坑：① `unquote` 不还原 `+`（要用 unquote_plus），否则 `18+Sep+2026+14:30` 认不出；② strptime 对 `%H%M` 过于宽容会把 `18` 当 01:08 → 判定日期时间一律用严格正则；③ 字段名含 "Facilities" 的 `boMakeBookFacilities[0].startDateTime` 会被 facility 规则抢先劫持 → 改为**先按值判类型、再看字段名**。
- 安全闸门：占位符取不到值时 `BookingNotCalibrated` **拒绝发送**（绝不把 `{facilityId}` 字面量发给学校）；302 跳非登录页 → 判定「结果不明」，记 state 后**停止重试**并推送让人工确认（保护押金）；连续会话失效上限 3 次（修复前 120 秒内重登 41 次，有风控/锁号风险）。
