## 从「抢一节体育课」扩到「抢所有 fitness」：Activity 维度 + 本地选课 UI
用户需求：POSS 的 make_book.do 页面有 Activity / Date / Center 三个下拉框，
要求这三个都能自己选，并要一个「像 POSS 那样点选要抢哪一节课」的 UI。

### 先说数据模型（这才是真问题）
原代码把 X123/X202 焊在 `gyms` 里、`actvId:101`/`dataSetId:18` 当常量 ——
所谓「Activity 下拉框」在代码里根本不存在。所以先做模型改造，UI 只是表皮。

### 新增 `booking.targets`（显式目标）
- 每项：`{ctrId, name, date, from, to, activity, actvId, dataSetId}`
- **放位日 = 目标日期 − lead_days 的 trigger_time**（POSS 只放今天起 8 天）。
  `_target_release_dt()` / `plan_jobs()` / `_job_from_target()` / `slot_matches_job()`。
- 非空时 `booking_phase` 不再看 `trigger_days`，只看「今天是不是某个目标的放位日」。
  Actions 的 `29 0 * * *` cron 本来就是**每天**跑，所以任意放位日都能接住。
- 空时保持旧的派生逻辑（今天+lead_days、同星期几、全部馆）—— 旧配置零改动。
- **抢到一个目标不再收工**，继续抢下一个（要抢多节）；只有 `inconclusive` 才全线停手。
- 去重从「按日」改成「按目标」：`state["booked_targets"]["{ctrId}|{date}|{from}"]`。
- 蹲守范围跟随 targets：`watch_scopes()` 返回 targets 里出现过的 (ctrId, actvId, dataSetId) 组合，
  `fallback_targets()` 带上精确日期。

### 新增 `poss_ui.py`（本地选课 UI）
- 本地 `http.server`（只绑 127.0.0.1，端口 8765）+ 单页 HTML，无新增依赖。
- `/api/meta` 登录后抓 `make_book.do` → `parse_selects()` 解析所有 `<select>` →
  按 name 关键词归角色（activity/dataset/center/date/other）。
- `/api/timetable` 拉时间表 → `build_grid()` 摊成 日期×时段 网格；
  `/api/targets` 校验后写回 config.json。
- 配色对齐 POSS：灰=不可用 / 洋红=$0+可退押金 / 蓝=收费 / 浅蓝=价格未知 / 极浅=原始数据没这个时段。
- 每个目标 chip 显示它自己的放位日，避免「点了 10-14 却不知道要 10-07 去抢」。

### 踩到的坑（都值得记住）
1. **`_parse_date()` 返回 `date` 不是 `datetime`** —— 新调度代码写 `.date()` / `.replace(hour=)`
   直接崩。写日期计算前先确认这个。
2. **UI 网格的列不能拿页面 date 下拉框的选项**。POSS 那个框是「搜索起始日」，
   选项可能只有两三条；照它画会缺列。正确做法：列 = 从选定起始日算 8 天。
3. **抓来的 `selected` 状态重建 option 时会丢**。`fillSelect` 必须显式
   `o.selected = true`，否则 Activity 停在「-- 请选择 --」上，保存出去的目标没有活动。
4. **灰色格子必须可点**。现在不可订 ≠ 放位那刻不可订；抢位目标本来就是给未来定的。
   一开始做成 `cursor:default` 会让整个 UI 在窗口没开时完全没用。
5. 裸属性 `<option selected>` 没有 `="..."`，`_attrs` 正则抓不到，要单独判 `"selected" in attrs_text`。
6. `_validate_booking_targets` 校验失败时**不能落盘**，否则 Actions 里直接炸。
7. 两个模块各自维护 `CONFIG_FILE` 会分叉 → 统一成 `poss_ui.config_path()` 读 `M.CONFIG_FILE`。

## 全部配置搬进 UI（同日 13:00）
用户：「配置也都放到 ui 里面不从配置文件单独配置了」。目标 = UI 成为唯一配置入口。

### 后端
- `with_defaults(cfg)` —— **一个函数补齐三处默认值**，`effective_config()` / `save_config()` /
  `api_meta()` 全走它，别再各写一份 setdefault。
  关键：`request` 的默认值住在 `poss_client.DEFAULT_BODY`（bookType/dataSetId/actvId…），
  不补的话 UI 上那几个框是空的 —— 用户看到「没配」，实际有生效值。
- `deep_merge(base, patch)` + `GET/POST /api/config`：**先合并 → 补默认 → 校验 → 写**，
  校验不过绝不落盘（坏配置进仓库、CI 才炸是最烦的失败方式）。
- `GET/POST /api/template`：复用 `calibrate.import_curl()` + `to_curl()`，
  写进 `.curl` 文件而**绝不写进 config.json**（模板可能残留会话凭据痕迹，而 config.json 要进仓库）。
- `template_status()`：每步导入了没有 + 字节数。UI 顶部据此挂横幅
  「模板不全 —— 现在只会蹲守提醒，不会真抢」。**没有这个提示，用户会以为配好了其实没配。**

### 前端
- 新增「设置」面板：常用（两个开关 + 6 个数字/时间框）+ `<details>` 高级
  （触发日 toggle / 默认时段 / 场馆列表 / 请求参数 / 关键词 / 结果页 / 蹲守目标 / 预订流程 / 模板导入）。
- 「恢复默认值」要**保住 targets** —— 目标不是默认值，别给清了。
- 设置区任何 input/change 都标脏，保存键亮琥珀点。

### 踩到的坑
1. **`.rows` 用 `auto-fit` 会折叠空轨道**：2 个开关那行变成 2 列各占一半，
   跟下面 6 个数字框的列宽对不齐。**改 `auto-fill`** 让所有行共享同一套轨道。
2. **隐形默认值（第二次踩）**：`DEFAULT_BOOKING["failure_keywords"]` 是 `[]`，
   而真正生效的是 `poss_client.DEFAULT_FAILURE_KEYWORDS` → UI 显示空、代码在用 24 个词。
   修法：`DEFAULT_BOOKING` 直接 `list(DEFAULT_FAILURE_KEYWORDS)`，**一份来源**。
   → 凡是「代码里有内置默认、配置里留空」的地方，UI 必须显示**生效值**，否则用户被误导。
3. 测试里我一开始断言 `plan_jobs` 会按 lead_days 从今天推 —— 错了：
   有 targets 时按各自放位日算，跟今天无关。测试写错，代码是对的。
4. `_validate_config` 只在 `booking.gyms` 非空时才校验引用关系；`[]` 时不校验。测这个要先设上。

## 登录凭据也搬进 UI（同日 13:10）
用户问：「登陆部分你是怎么处理的，用户名和密码填哪里?」
—— 一问问出我上一轮的漏项：说了「配置全放 UI」，却把**最该放进去的登录**留在 `.env` 里要手编。

### 设计
- `GET/POST /api/account`：读写 `.env`（**不是 config.json** —— 那要提交进仓库）。
- `write_env()` 逐行改：**保留原有注释与无关的键**，只替换命中的，缺的追加；
  写完 `chmod 0600`；同时更新 `os.environ` 让它立刻生效。
- **密码永不回传前端**：`account_status()` 只给 `password_set: bool`，
  页面用 placeholder 显示「已设置 · 留空 = 不改」。
- **密码框留空 = 不改**：不然用户每次调通知渠道都会把密码清掉。
- 通知渠道（PushPlus/Server酱/SMTP）一并进 UI + 「发一条测试通知」按钮。
- `monitor.reload_notify_env()`：`PUSHPLUS_TOKEN` 这些是**模块级常量**，进程启动读一次；
  UI 写完 .env 不刷新的话，界面显示「已配置」、实际发的还是旧值。
- `SMTP_PORT` 用 `os.environ.get(...) or "465"` —— 空字符串会 `int('')` 抛异常。

### 修掉一个会丢数据的 bug
`loadConfig()` 原来只在**登录成功后**（`loadMeta()` 里）调用 →
没配账号时「设置」面板一片空白 → 此时点「保存设置」会把空值写进 config.json，
**直接清掉用户配置**。config.json 与 POSS 会话毫无关系，改成启动时无条件先加载。
→ 教训：**UI 里「因为前置条件没满足所以没加载数据」的表单，必须配一个
「数据没加载就别让保存」的闸门**，否则空表单就是一颗数据清除按钮。

### 另一个坑：多处写同一个 banner
账号警告、模板警告、抓取错误三处各自 `$("#banner").innerHTML = ...`，
互相覆盖 —— 先写的那个永远看不见。收敛成单一写入口 `renderBanner()`，
用一个 `META_ERROR` 变量收集。

## 修「换选项格子不变」（同日 13:20）
用户反馈：换 Activity/Center，可订时间表毫无变化。

**定位手法（值得记住）：先抓请求，别先改代码。**
用 playwright 监听 `/api/timetable`，再依次 selectOption 三个下拉框：
4 次请求全发了、`ctrId`/`actvId`/`start` 都在变 → 排除「没刷新」。
问题在别处，且是两个叠在一起：

### 1. 【真 bug】参数名写死
`fetchGrid()` 里 `q.set("actvId", ...)` / `q.set("dataSetId", ...)` 是硬编码的，
**没用抓到的 select 真实 name**。页面字段名 ≠ AJAX 接口参数名时
（如页面叫 `activityId`、接口要 `actvId`），服务端直接忽略该参数 →
表现就是「换了选项格子不变」。
**修法：页面名 + API 规范名两个都发**（`URLSearchParams.set` 同名只留一个），
服务端认哪个用哪个，多发的那个不认识会自己忽略。只发一个都可能坏。

配套：
- `allowed_param_keys()` = 已知默认键 ∪ 页面真实 select 名 − PROTECTED。
  站点换字段名能自动跟上，同时挡住乱塞参数。
- `PossClient.timetable` 去掉固定白名单 `OVERRIDABLE`，改挡 `PROTECTED_BODY_KEYS`
  （`CSRFToken`/`fbUserId`/`ctrId`/`searchDate` 不许被 params 覆盖 ——
  否则等于让人从 URL 里改会话身份）。

### 2. 【我的锅】假数据实例骗了人
给用户看的 8766 预览里，`FakeClient.timetable` 完全忽略参数、永远返回同一套数据。
用户拿它判断产品，当然以为坏了。**演示数据必须真的响应参数**，
否则预览不是预览，是误导。
修完：换中心 → 行数变（不同营业时间）；换活动 → 配色/可订数变（不同 sparse/free_before）。

### 3. 加了「当前视图」说明
网格上方显示「活动 · 中心 · 起始日」，加读取中置灰态。
**没有这个，用户无法判断是没刷新、还是数据本来就一样** —— 这是反馈能成立的前提。

### 定位陷阱
探针第一版只数「有数据的格子」，结果换活动时数字纹丝不动（因为两个活动行数相同、
只是颜色不同）→ 差点误判成没生效。改成**按 cell class 分类计数**才看见差异。
教训：**统计指标要能区分你要区分的差异**。

测试：test_ui.py 85 项（新增参数透传 7 项）、test_booking_schedule.py 56 项
（新增令牌保护 5 项）。共 141 项全绿。提交 be9a375。
